Heat Risk ABM Model - Summer 2025 Development Notes

Author

Project contributors

Published

August 27, 2025

Overview

This document provides comprehensive documentation for the Heat Risk Agent-Based Model (ABM) developed in Summer 2025. The model simulates resident behavior during extreme heat events in Hennepin County, Minnesota, predicting whether individuals stay home or move to cooling centers.

Key Improvements in 2025 Version

  • Parallel chunk processing for improved performance
  • External AC data integration from market-based sources
  • SLURM array job support for MSI supercomputing
  • Preprocessed data pipeline eliminating database dependencies
  • PRISM temperature data integration for accurate heat modeling
  • Comprehensive validation framework against real-world visitation data

Input Data

Core Datasets

1. Parcel Data

  • Source: Hennepin County parcel dataset (~400,000 parcels)
  • Format: PostGIS database or preprocessed pickle file
  • Key fields:
    • pid: Parcel ID
    • geometry: Parcel boundaries
    • medianhhi: Median household income
    • age demographics: ageunder18, age18_39, age40_64, age65up
    • poptotal: Total population
    • block_group_id: Census block group identifier

2. Temperature Data (PRISM)

  • Source: PRISM Climate Group, Oregon State University
  • Resolution: 800m or 4km grid
  • Coverage: May 1 - September 30 for years 2020, 2021, 2023, 2024
  • Variables: tmax, tmin, tmean (maximum, minimum, mean temperature)
  • Format: GeoTIFF rasters in Celsius (converted to Fahrenheit)

3. Air Conditioning Data

  • External source: data/raw/Parcel_AC/hennepin_parcel_ac_avail.csv
  • Fields: pid, ac_available (market-based AC availability)
  • Coverage: 346,704 parcels with external AC data
  • Fallback: Census-based AC probability model

4. Cooling Centers

  • Source: Validated cooling center locations
  • Fields: name, geometry, type, validate_tag
  • Special tags: Libraries, cooling centers, emergency departments

Data Preprocessing

Parcel Data Extraction (01_save_parcels_from_db.py)

The model uses preprocessed parcel data stored as a pickle file to avoid repeated database queries:

# Creates: data/preprocessed_data/parcels_prepared.pkl
# Contains: GeoDataFrame with all parcel attributes
# Size: ~200MB
# Load time: <1 second vs 30+ seconds from database

Key features of preprocessing: - Extracts parcels with all demographic attributes - Calculates nearest cooling centers for each parcel - Stores cooling center distances - Preserves geometry for spatial operations - Includes metadata with extraction timestamp and version

Why use pickle files? - Speed: 30x faster loading than database queries - Portability: No database credentials needed - Consistency: Same data across all runs - MSI compatibility: Works on compute nodes without database access

PRISM Temperature Data

Download Process (oneoff/download_prism_data.py)

Downloads daily temperature data from PRISM FTP server:

# Configuration
YEARS_TO_DOWNLOAD = [2020, 2021, 2023, 2024]
MAX_WORKERS = 8  # Parallel download threads

# Downloads to: data/raw/prism/
# File format: tmax_prism_YYYYMMDD_800m.tif

Download specifications: - Protocol: FTP (ftp.prism.oregonstate.edu) - Data type: Daily gridded climate data - Coverage: Continental US (CONUS) - Format: BIL format in ZIP archives, extracted to GeoTIFF

Processing Pipeline (oneoff/02_process_prism_raw_to_intermediate_prism.py)

Processes raw PRISM data for model consumption:

# Input: data/raw/prism/tmax_prism_YYYYMMDD_800m.tif
# Output: data/validate_data/intermediate/prism/tmax_hennepin_YYYYMMDD_500m.tif

Processing steps: 1. Reprojection: Convert to EPSG:26915 (UTM Zone 15N) 2. Resampling: Resample to 500m resolution matching reference raster 3. Clipping: Crop to Hennepin County boundaries 4. Unit conversion: Convert Celsius to Fahrenheit 5. Validation: Verify output matches reference specifications

Parallel Processing Architecture

The model divides parcels into chunks for parallel processing:

# 400,000 parcels ÷ 30 workers = ~13,333 parcels per chunk
# Each chunk processes independently
# Results merged after completion

Process flow: 1. Load preprocessed parcel data 2. Extract temperatures from PRISM raster 3. Split parcels into chunks 4. Process chunks in parallel using ProcessPoolExecutor 5. Aggregate results across chunks 6. Repeat for multiple runs (ensemble approach) 7. Calculate statistics and save outputs

Improvements Over Original Model

Original: Model_final_LR_edit_adapt_from_ipynb.qmd

Limitations: - Sequential processing (5-10 minutes per run) - Database dependency for each run - Limited to 5 ensemble runs - Manual temperature raster selection - No external AC data integration

New Model Improvements

1. Performance Enhancements

  • 30x faster: Parallel chunk processing
  • Preprocessed data: Eliminate database overhead
  • Batch processing: Multiple dates in single execution
  • Memory efficient: Streaming results to disk

2. Data Integration

  • External AC data: Market-based AC availability
  • PRISM integration: Automated temperature data pipeline
  • Validation framework: Compare against real visitation

3. Scalability

  • SLURM support: Process 368 dates simultaneously
  • Configurable workers: Scale from laptop to HPC
  • Ensemble size: 1000 runs vs 5 runs

4. Output Quality

  • Comprehensive statistics: Per-run and ensemble metrics
  • Multiple formats: Shapefile, CSV, JSON metadata
  • Organized structure: Year/date folder hierarchy

def calculate_metrics(predicted, actual):
    """Calculate validation metrics"""
    
    return {
        'rmse': root_mean_square_error(predicted, actual),
        'mae': mean_absolute_error(predicted, actual),
        'correlation': pearson_correlation(predicted, actual),
        'bias': mean(predicted - actual),
        'relative_error': mean(abs(predicted - actual) / actual),
        'peak_accuracy': peak_detection_accuracy(predicted, actual)
    }

GeoDataFrame with parcel-level results: - pid: Parcel identifier - geometry: Parcel boundaries - temperature: Extracted temperature - prob_move_mean: Average movement probability - decision_majority: Final decision (stay/move) - decision_stability: Consistency across runs - cooling_center: Chosen destination if moving

Best Practices and Tips

Data Management

  1. Always use preprocessed parcels - Don’t query database repeatedly
  2. Process dates in batches - Reduce I/O overhead
  3. Clean up intermediate files - Prevent disk space issues
  4. Version control outputs - Use timestamp folders

Performance Optimization

  1. Chunk size tuning - Balance between parallelism and overhead
  2. Worker count - Use n_cores - 2 for stability
  3. Memory management - Clear objects after processing
  4. Disk I/O - Use SSD for temporary files

Validation

  1. Check convergence - Ensure decisions stabilize
  2. Verify temperatures - Confirm Fahrenheit conversion
  3. Validate AC data - Check coverage percentage
  4. Compare distributions - Movement rates should be realistic

Troubleshooting

Common Issues

Issue: “Preprocessed parcels file not found” - Solution: Run 01_save_parcels_from_db.py first

Issue: “Temperature raster missing for date” - Solution: Check PRISM data download and processing

Issue: “Memory error during parallel processing” - Solution: Reduce worker count or chunk size

Issue: “SLURM job timeout” - Solution: Request more time or reduce runs per job
